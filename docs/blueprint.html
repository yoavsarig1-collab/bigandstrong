Requirement 01

Periodization

Program → blocks → weeks → days → sessions. Parameters (sets, reps, RIR, intensity, rest) change per week within a block. Exercises "enter in week 5." The structure carries the logic.

Requirement 02

Substitutions with reasons

Your "iterations." Trap-bar instead of conventional deadlift; supported row instead of bent-over — each swap tied to a cause (a limitation, or later home vs. studio vs. gym). The reason travels with the swap.

Requirement 03

Autoregulation loop

The plan reacts to the athlete: morning-pain trend → freeze or progress; velocity drop of 20–25% ends a set. Trainee input feeds back into what they do next.

Requirement 04

Testing & goals

Batteries at weeks 2 / 6 / 12 with a fixed protocol, gate conditions to advance a block, and measurable targets (CMJ +3–5 cm, sprint −0.1 s). Progress is defined, not vibes.

The one hard modeling decision — substitutions

An Exercise instance points at a library Exercise, and that exercise carries Variations tagged by reason. So the trainee taps "I'm at home" or "this hurts" and the app offers the coach-approved swap — the same mechanism that already produced trap-bar over conventional deadlift in Jonathan's plan. Get this relationship right and the whole "iterations" feature falls out of it for free.

Get right first Your stated priority

Trainee sign-in & the first workout

A trainee's experience is their program on a screen. The bar: from an invite to logging their first set, with zero passwords and no confusion — even on gym wifi that barely works.

01 · INVITE

Coach adds them

You enter a name + phone/email. They get one link. No account form to fill.

02 · TAP

Magic link

Tapping the link creates the account and signs them in at once — the pattern that took Notion's completion from 64%→87%.

03 · INSTALL

Add to Home Screen

A short prompt to install the PWA. This is also what unlocks push notifications on iPhone.

04 · TODAY

Their week, their day

Opens straight to today's session: warmup → strength → core, each exercise with target sets×reps and RIR.

05 · LOG

Check & note

Tick each set, log weight/reps, drop their morning-pain score and a note back to you. Works offline.

Two things make or break this and both have clear answers below: passwordless invite auth (so onboarding isn't a wall) and offline-first logging (so a dead signal between sets never loses a workout). Row-level security means a trainee only ever sees their own data — enforced by the database, not by hoping the UI hides it.

The other side

The coach side

This is where today's coach.html grows up. The check-in calendar you already have becomes the review surface; a program builder feeds it.

Author

Program builder

Compose a program once — blocks, weekly parameters, sessions, exercises, substitutions — then assign it to a trainee with a start date. Reuse it for the next athlete.

Review

Two check-ins a week

Exactly your workflow: the week dashboard, colour per trainee, who did what, their notes and pain scores surfaced — no digging.

React

Adjust the plan

Pain trending up? Freeze load or swap an exercise for that athlete without touching the template. No in-app chat — the trainee's check-in notes are the channel back to you.

The research, defended

Platform decisions

Each row is a call I'm making, why, and the current source behind it. Verdicts are mine to argue with — that's the point of writing them down.

DecisionVerdictWhySource
Delivery: PWA vs native PWA now On iOS 26 a home-screen site opens as a real app and can send push (since 16.4, once installed). One codebase covers all devices. Trade-off: no App Store, no background sync — neither blocks a v1 coaching app. [1][2]
Backend: Supabase vs Firebase Supabase A periodized program is deeply relational (joins across program → week → exercise → log). Postgres + row-level security fits it directly; Firestore would force denormalization. Free tier: 500 MB DB, 50k monthly users, unlimited API calls. [3][4]
Auth: how trainees get in Invite + magic link Lowest-friction onboarding for an invited audience; removing passwords measurably lifts completion. Email magic link primary; SMS only as fallback (agencies advise against SMS-only). Passkeys can come later for returning users. [5]
Offline strategy Local-first Treat offline as the default, sync as optimization. Start simple (IndexedDB queue + sync on reconnect); adopt a sync engine like PowerSync only if conflict handling gets real. The gym is the whole use case, so this isn't optional. [6]
Hebrew / RTL Foundation Set dir="rtl" at the root; use logical CSS (margin-inline, text-align:start) so layout mirrors automatically; flip only directional icons; Heebo/Assistant for Hebrew type; keep numbers & kg/%/RIR LTR inside RTL text. [7]
Frontend framework Decide at build The current apps are hand-written single-file HTML. That won't scale to auth + sync + a program builder. Lean recommendation: a light framework (Svelte or React) + Vite, with first-class RTL and PWA support. Confirmed when Phase 1 starts. —

Security is a database job, not a UI job

Because trainee data is health-adjacent, access is enforced with Postgres row-level security: a trainee can read and write only rows that belong to them; a coach sees only their own athletes. The UI never becomes the thing standing between one client and another's data.

Order of operations

Roadmap

Sequenced so something real is usable at the end of every phase, and so the priority you named — trainees signing in and training — arrives early rather than after a year of backend.

0

Model Jonathan's program start here

Prove the data model by encoding one real program into it — on paper / JSON, before any backend.

  • Turn the 12-week plan into the Program → Block → Week → Session → Exercise shape.
  • Encode the substitutions and their reasons.
  • If it fits cleanly, the model is right. If it fights, fix it now while it's cheap.
1

Backend + trainee sign-in

A trainee can be invited, sign in with a magic link, and see a program that's really theirs.

  • Stand up Supabase: schema, row-level security, auth.
  • Coach invite flow → magic link onboarding.
  • Read-only "my week / my day" trainee view of an assigned program.
2

Logging, offline, check-ins

Trainees train from it for real — the whole reason it exists.

  • Set logging, morning-pain score, notes back to coach.
  • Offline-first capture with sync on reconnect.
  • Substitution picker: home / studio / "it hurts."
3

Coach program builder

Author and assign programs in-app instead of by hand — and fold in your existing calendar.

  • Build blocks / weeks / sessions / substitutions visually.
  • Assign to a trainee against a start date.
  • Migrate the coach.html check-in dashboard onto live data.
4

Polish & depth

The things that make it feel finished.

  • Testing batteries, goal tracking, progress charts.
  • Push notifications, exercise videos, optional full-English UI.
  • Autoregulation prompts from pain / velocity trends.
Settled · Sep 2026

Decisions — locked

The scope questions are answered. These now constrain the build; each one made the app simpler, not more complex.

Decided A

Language

Hebrew UI, right-to-left. Exercise names default to English — the way the program already writes them.

→ English exercise names, Hebrew everything else.

Decided B

Maintainer

You maintain it. So the stack is chosen for the fewest moving parts a non-team can keep running.

→ Optimize for one person.

Decided C

Messaging

No in-app chat or comment threads. The trainee's check-in notes are the only channel back to the coach.

→ Notes only, no messaging.

Decided D

Scale

Tens of trainees. Sits comfortably inside free tiers and rules out any premature scaling work.

→ Design for tens, not thousands.
